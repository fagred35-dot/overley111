# Overley — архитектура

**Версия:** 0.1 · **Родительский документ:** [`PLAN.md`](PLAN.md) · **Стек:** Rust (ядро) + Tauri 2 / React (UI настроек)

Документ описывает технические решения настолько, чтобы по нему можно было писать код без дополнительных исследований. Спорные места помечены как **[SP]** — проверяются спайком на M0.

---

## 1. Инварианты системы

Эти пять утверждений нарушать нельзя ни в одной фиче. Любой PR, который их ломает, отклоняется.

1. **I1. Нет доступа к процессу игры.** Мы не открываем хендл на игру (кроме опционального `PROCESS_QUERY_LIMITED_INFORMATION` для уточнения пути, и это отключаемо), не читаем память, не инжектим, не хукаем её API, не симулируем в неё ввод.
2. **I2. Оверлей — пассивное окно.** Оно click-through, не берёт фокус, не участвует в Alt+Tab, не перехватывает ввод игры.
3. **I3. Статичный прицел стоит 0 CPU.** Если прицел не анимируется и мышь не влияет на него — перерисовок нет вообще, кадр не презентуется.
4. **I4. Система всегда возвращает пользователю курсор.** Любое изменение системного курсора обратимо: в коде (RAII-guard), при краше (watchdog-файл) и при следующем старте (проверка).
5. **I5. Никакого доверия внешним данным.** Всё, что пришло из буфера обмена/файла/ИИ, считается враждебным до прохождения валидации и лимитов.

## 2. Процессы, окна, потоки

Один основной процесс `Overley.exe` (single instance). Внутри — три окна и четыре потока.

```
Overley.exe
├─ Окна
│  ├─ OverlayWindow      (видимое во время игры; DComp+D2D; TOPMOST|TRANSPARENT|NOACTIVATE)
│  ├─ OsdWindow          (тосты поверх игры; то же, но меньше и с таймером; опционально)
│  └─ SettingsWindow     (WebView2; создаётся по требованию, DESTROY при закрытии)
├─ Потоки
│  ├─ UI/Message thread  (Win32 message loop, все окна, трей, хоткеи)
│  ├─ Render thread      (D2D/DComp: compile → draw → present) [SP: можно совместить с UI thread]
│  ├─ Input thread       (Raw Input sink + опрос GetPhysicalCursorPos 500–1000 Гц)
│  └─ Watcher thread     (снапшот процессов 1–2 Гц, foreground-опрос 10 Гц, watchdog курсора)
└─ Вспомогательные процессы WebView2 (msedgewebview2.exe) — живут только пока открыто окно настроек
```

**Почему один процесс, а не два (оверлей + UI отдельно):** WebView2 и так живёт в собственных процессах и изолирован; разделение нашего ядра на два процесса добавило бы IPC и сложность восстановления состояния. Окно настроек уничтожается при закрытии → WebView2-процессы завершаются → в игре остаётся только ядро. **[SP-1]** измерить на M0: реально ли достигается ≤ 25 МБ после уничтожения окна.

**Резервный вариант:** если WebView2 окажется нестабильным источником просадок (его процессы могут влиять на систему), выносим SettingsWindow в отдельный процесс `Overley.UI.exe`, а `Overley.exe` становится «голым» ядром с оверлеем. Архитектурно закладываем это заранее: весь обмен ядро↔UI идёт через один интерфейс `ControlChannel` (§11), который одинаково реализуется и in-process (Tauri commands/events), и межпроцессно (named pipe).

**Watcher-процесс (P2, FR-F05):** отдельный `Overley.Watcher.exe` ≤ 8 МБ, который может поднять ядро при старте игры, если пользователь закрыл приложение. Не в v1.

## 3. OverlayWindow: рецепт окна

### 3.1 Стили

```rust
// Псевдокод на windows-rs (проверяется на M0)
let ex = WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOPMOST
       | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW;   // TOOLWINDOW -> не виден в Alt+Tab
let st = WS_POPUP;                              // без рамки, без заголовка
// Дополнительно для DComp-рендера без redirection surface:
let ex = ex | WS_EX_NOREDIRECTIONBITMAP;
```

- `WS_EX_TRANSPARENT` — клики проходят сквозь окно (обязательно вместе с `WS_EX_LAYERED`).
- `WS_EX_NOACTIVATE` — окно не активируется при клике/показе, фокус игры не теряется.
- `WS_EX_TOPMOST` + периодический re-assert (`SetWindowPos(HWND_TOPMOST, SWP_NOMOVE|SWP_NOSIZE|SWP_NOACTIVATE)`) по событию смены foreground-окна — игры иногда «перетягивают» topmost на себя.
- Размер/позиция = прямоугольник активного окна игры (borderless) или весь монитор (режим «всегда на весь экран»).

### 3.2 Композиция и рендер

```
D3D11 device (feature level 11_0, BGRA support)
  └─ DXGI swapchain: CreateSwapChainForComposition
       Format = B8G8R8A8_UNORM (или R10G10B10A2/R16G16B16A16_FLOAT для HDR)
       AlphaMode = DXGI_ALPHA_MODE_PREMULTIPLIED
       SwapEffect = DXGI_SWAP_EFFECT_FLIP_SEQUENTIAL
       BufferCount = 2, Flags = FRAME_LATENCY_WAITABLE_OBJECT
  └─ DComp: IDCompositionDevice → target(surface=hwnd) → root visual → swapchain visual
  └─ D2D: ID2D1DeviceContext поверх backbuffer (premultiplied alpha)
```

- **Present:** по waitable object, синхронно с vblank; `MaxFrameLatency = 1`. Без vsync-разрывов, без tearing (оверлей не должен рвать кадр игры).
- **Dirty-политика (инвариант I3):** рендер-поток спит на `WaitForSingleObject(render_event)`. Событие выставляется только когда: (а) изменился пресет/слой, (б) есть активная анимация, (в) пришли новые данные реактивности, отличающиеся от прошлых, (г) сменился монитор/размер окна. Если ничего не изменилось — present не вызывается вовсе.
- **Статичный путь:** весь `DrawList` рендерится один раз в `ID2D1Bitmap`/offscreen-поверхность размера холста (например 192×192), дальше в кадре делается один `DrawImage` с нужной позицией и глобальной прозрачностью. Стоимость ≈ одна операция blit, но и она не вызывается без dirty-события.
- **Fallback `UpdateLayeredWindow` (FR-A12):** для машин без рабочего DComp/DXGI (старые драйверы, RDP, виртуалки). Рендерим в CPU-битмап (`tiny-skia`) и обновляем layered window. Ограничение: обновления на каждый кадр дороги → в этом режиме анимации автоматически даунгрейдятся до 30 Гц, о чём пишем в UI.

### 3.3 Позиционирование

| Режим | Источник координат | Комментарий |
| --- | --- | --- |
| `center` | Центр клиентской области foreground-окна игры (`GetWindowRect`/`DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`) | В FPS курсор скрыт самой игрой, прицел всегда в центре камеры. Если игра в borderless на весь монитор — центр монитора |
| `cursor` | `GetPhysicalCursorPos` (опрос) + Raw Input для дельт/кнопок | Физические координаты, не логические: иначе на смешанных DPI будет сдвиг |
| `auto` | `center`, если активное окно совпало с профилем игры; `cursor` иначе | Поведение по умолчанию для профилей |

Преобразование координат: физические px → координаты окна оверлея → координаты холста прицела с учётом `canvas.origin`, `behavior.offset`, `dpiScale`. Все вычисления в целых/`f32`, с `pixelSnap` при необходимости.

### 3.4 Мультимонитор, DPI, HDR

- Per-Monitor DPI Awareness v2 в манифесте.
- Оверлей привязан к выбранному монитору; при смене foreground-окна на другой монитор — переезжаем (с дебаунсом, чтобы не мигать при быстром Alt+Tab).
- Слушаем `WM_DISPLAYCHANGE`, `WM_DPICHANGED`, `WM_SETTINGCHANGE`; при получении — полный пересоздание swapchain и пересчёт масштаба.
- HDR: если монитор в HDR-режиме (`DXGI_OUTPUT_DESC1.ColorSpace`), используем `R16G16B16A16_FLOAT` + scRGB, иначе цвета будут выбелены/перенасыщены. Fallback — SDR-цепочка.
- Разрешение/refresh rate меняются на лету (игры это делают при alt-tab) → пересоздание swapchain по событию, не по таймеру.

## 4. Ввод: как получаем позицию и кнопки мыши

Требование: задержка ≤ 1 кадр, но **без низкоуровневых хуков** (WH_MOUSE_LL виден античитам и может быть расценен как вмешательство в ввод).

1. **Raw Input (основной источник кнопок и дельт).** Message-only window + `RegisterRawInputDevices` с `RIDEV_INPUTSINK` — получаем `WM_INPUT` глобально, даже когда фокус у игры. Даёт состояние кнопок, wheel, относительные перемещения. Не хук, DLL никуда не внедряется.
2. **Опрос абсолютной позиции (основной источник координат).** `GetPhysicalCursorPos` в цикле input-потока на 500–1000 Гц (стоимость — доли процента ядра, вызов тривиальный). Причина: Raw Input для относительных мышей даёт дельты, которые расходятся с реальной позицией курсора из-за ускорения/клиппинга/игры с raw input.
3. **Сглаживание.** EMA по позиции (α настраивается, по умолчанию 1.0 = без сглаживания, чтобы не добавлять задержку) и EMA по `mouseSpeed` для реактивных каналов (`reactive.smoothingMs`).
4. **Расчёт каналов для DSL:** `mouseSpeed` (px/с), `mouseDX/DY` (за кадр), `mouseButton1..5` (0/1), `wheel` (последняя дельта, затухает за 250 мс), `idle` (секунды с последнего движения), `t` (секунды от старта оверлея), `focused` (1, если целевое окно в фокусе), `fps` (оценка частоты презентаций).

**Явно не делаем:** не подписываемся на ввод игры через хуки, не блокируем и не модифицируем события, не используем `SendInput`.

## 5. Скрытие и восстановление системного курсора

Самая опасная часть UX (риск R4). Три уровня:

| Стратегия | Механизм | Обратимость | По умолчанию |
| --- | --- | --- | --- |
| `none` | ничего не меняем; прицел рисуется рядом/поверх курсора | идеальная | ✅ да |
| `overlay-only` | пока оверлей активен, в пределах нашего окна курсор не отображается (`SetCursor(NULL)` в обработчике `WM_SETCURSOR` + `ShowCursor(FALSE)` в нашем потоке). Реально работает только если курсор оказывается над нашим окном, а оно click-through → **[SP-2]** проверить; вероятный итог: strategy практически бесполезна для игр, оставляем как «честную» опцию | идеальная | — |
| `system-blank` | `SystemParametersInfo(SPI_SETCURSORS)` с набором пустых курсоров; перед этим сохраняем оригиналы через `SPI_GETCURSORS` в `%APPDATA%\Overley\cursor-backup\*.cur` | требует восстановления | ❌ выключено, включается с предупреждением |

**Механизм гарантии восстановления (I4):**

1. RAII-guard `CursorRestore` в Rust: `Drop` вызывает восстановление. Покрывает нормальное завершение и большинство паник.
2. **Watchdog-файл** `%APPDATA%\Overley\cursor.lock` с PID, временем, путями к бэкапам. Создаётся перед подменой, удаляется после восстановления.
3. **При старте приложения:** если lock-файл существует и PID мёртв → немедленно восстанавливаем курсоры из бэкапа, показываем OSD «Курсор восстановлен после сбоя».
4. **Сторонний watchdog:** если включён `system-blank`, создаётся scheduled task / отдельный поток с таймером 3 с, проверяющий живость основного потока; при зависании — восстановление.
5. **Автовосстановление по событиям:** выход из игры, сворачивание, alt-tab, закрытие приложения, «паника»-хоткей, ошибка рендера — всё восстанавливает курсор.
6. **Документация:** в FAQ и в README — инструкция «если курсор пропал: перезапустите Overley / запустите `overley.exe --restore-cursor`». Отдельная CLI-команда, работающая даже без ядра.

Дополнительно: большинство FPS сами скрывают курсор в матче, поэтому для игрового сценария `center` подмена курсора обычно вообще не нужна. Это надо доносить в онбординге.

## 6. Детект приложений и профилей (авто-запуск без инжекта)

### 6.1 Источники сигналов

| Сигнал | API | Частота | Стоимость | Что даёт |
| --- | --- | --- | --- | --- |
| Список процессов | `CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS)` | 1–2 Гц | микро-миллисекунды | имена процессов для матчинга профиля |
| Активное окно | `GetForegroundWindow` → `GetWindowThreadProcessId` | 10 Гц или через `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` | почти ноль | PID + HWND активного окна |
| Имя процесса по PID | `QueryFullProcessImageName` с `PROCESS_QUERY_LIMITED_INFORMATION` | по изменению PID | открывает хендл (минимальные права) | точный путь для матчинга; **опция «без хендлов»** — тогда матчим только по имени из снапшота |
| Режим окна | `GetWindowRect` + `DwmGetWindowAttribute` + `SHQueryUserNotificationState` | по смене окна | ноль | borderless vs FSE-эвристика, «не беспокоить» |
| Полноэкранность | сравнение rect окна с rect монитора + отсутствие рамки + `QUNS_RUNNING_D3D_FULL_SCREEN` | по смене окна | ноль | детект FSE для подсказки |

`SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` с `WINEVENT_OUTOFCONTEXT` — это **не** инжект: колбэк выполняется в нашем процессе, DLL в чужие процессы не ставится. Это предпочтительный источник (событийный, без опроса). Опрос 10 Гц — fallback.

### 6.2 ProfileEngine

```
вход: { foreground_pid, foreground_hwnd, process_list_snapshot, window_rect, fullscreen_state }
      │
      ▼
1. Матчинг профилей: точное имя exe → путь → wildcard-подстановка → приоритет правил
2. Исключения: список «никогда не показывать» (браузер, OBS, лаунчеры) — имеет приоритет
3. Дебаунс 250 мс: профиль должен удержаться, иначе игнорируем (защита от мигания при alt-tab)
4. Состояние: Inactive → PendingMatch → Active(profile) → Releasing
5. Действия на переходе Active: применить пресет (≤ 50 мс), показать оверлей, скрыть курсор (по профилю), OSD-тост
   Действия на Releasing: спрятать оверлей, восстановить курсор, сбросить анимации
6. Журнал последних 50 переходов (FR-F07) — доступен в UI «Почему оверлей скрыт?»
```

Правила профилей хранятся декларативно (`match: {exe: "cs2.exe", pathContains: "Steam\\steamapps\\common", anyOf: [...]}`), матчинг — детерминированный, с приоритетом: точный путь > точное имя > wildcard > глобальный профиль.

### 6.3 Автозапуск самого Overley

- **При входе в Windows:** Task Scheduler (предпочтительно: не светится в диспетчере автозагрузки как «Run», умеет условия «от сети/питания») или ключ `HKCU\...\Run`. Настраивается через `tauri-plugin-autostart`.
- **«Поднять оверлей, когда игра уже запущена»:** если приложение было закрыто, это делает watcher (P2) или пользователь вручную; в v1 — приложение стартует вместе с Windows и живёт в трее (стоимость — 10–15 МБ), что закрывает сценарий.
- **«Запустить игру из приложения» (FR-E07, P2):** обычный `CreateProcess` с рабочим каталогом игры. Никаких параметров, никаких хендлов. Это не инжект, но по умолчанию выключено, чтобы не плодить ложные срабатывания AV.

## 7. Хоткеи

1. **Основной механизм — `RegisterHotKey`.** Без хуков, безопасно с точки зрения античит-политик. Работает глобально, включая момент, когда фокус у игры (в большинстве случаев).
2. **Известное ограничение:** игры, эксклюзивно захватывающие ввод через raw input/DirectInput, могут не отпускать комбинации в систему. **[SP-3]** проверить в CS2/Valorant/Apex.
3. **Fallback (опция, по умолчанию выключена):** низкоуровневый `WH_KEYBOARD_LL` только для 1–3 комбинаций, с явным предупреждением в UI: «может конфликтовать с античитом/другими программами; включайте, только если стандартный режим не работает». В обработчике — никаких модификаций событий, только наблюдение и `CallNextHookEx`.
4. Набор: паника (скрыть всё), цикл пресетов, прямой выбор пресета 1–9, try-on 15 с, center/cursor toggle, открыть настройки, переключить оверлей.
5. Конфликты: при регистрации проверяем ошибку `ERROR_HOTKEY_ALREADY_REGISTERED` и показываем в UI, какой именно хоткей не зарегистрировался.

## 8. DSL-конвейер

```
Текст (JSON) ─┬─> 1. Normalize (снять ```json, найти первый объект, починить частые ошибки ИИ)
              ├─> 2. Parse (serde_json, лимит размера/глубины)
              ├─> 3. Schema validate (JSON Schema 2020-12 + семантические лимиты)
              ├─> 4. Semantic check (дубли id, target'ы bindings существуют, выражения из белого списка)
              ├─> 5. Compile -> DrawList (вектор операций) + AnimTracks + ReactiveBindings
              └─> 6. Cache: статичная часть -> ID2D1Bitmap; динамическая -> per-frame ops
```

### 8.1 DrawList

Плоский вектор операций, независимый от API отрисовки (один и тот же `DrawList` умеют исполнять D2D-бэкенд, `tiny-skia`-бэкенд для golden-тестов и CPU-fallback):

```rust
enum DrawOp {
    PushTransform { m: Mat3 }, PopTransform,
    SetOpacity(f32), SetBlend(BlendMode),
    FillRect { r: RectF, radius: f32, brush: BrushId },
    FillCircle { c: Point, r: f32, brush: BrushId },
    StrokeRing { c: Point, r: f32, w: f32, dash: Option<Arc<[f32]>>, brush: BrushId },
    StrokeLine { a: Point, b: Point, w: f32, cap: Cap, brush: BrushId },
    FillPoly { pts: Arc<[Point]>, closed: bool, brush: BrushId },
    StrokeArc { c: Point, r: f32, w: f32, a0: f32, a1: f32, cap: Cap, brush: BrushId },
    FillPath { path: PathId, rule: FillRule, brush: BrushId },
    DrawText { run: TextRunId, at: Point, brush: BrushId },
    DrawImage { img: ImageId, dst: RectF, tint: Option<Color> },
    DrawShadow { ... } // реализуется как blur-пасс в offscreen
}
```

Браши/пути/картинки/текстовые раны — в side-tables с id (чтобы компилятор не дублировал ресурсы и чтобы кэш переживал мелкие правки).

### 8.2 Expression VM

- Грамматика (полностью — в [`CROSSHAIR_DSL.md §7`](CROSSHAIR_DSL.md)): арифметика, сравнения, логика, тернарный оператор, белый список из 20 функций, каналы и `vars`.
- Компиляция один раз → стековая машина (RPN) на `f64`; исполнение — десятки наносекунд на выражение.
- **Безопасность:** собственный парсер (не `eval`, не JS). Идентификаторы — только из белого списка; неизвестный идентификатор = ошибка компиляции. Никаких обращений к памяти, никаких циклов, никаких вызовов наружу. Глубина рекурсии выражений ограничена, длина ≤ 240 символов.
- Все результаты клампятся (`reactive.range` обязателен, иначе отклоняем — см. негативный тест `07-reactive-without-guard.json`).
- `NaN`/`Inf` → значение по умолчанию + предупреждение в лог (не роняем рендер).

### 8.3 Анимации

- Единый monotonic clock (`QueryPerformanceCounter`), общий для всех треков.
- Трек = `{target prop, from/to или keyframes+times, duration, delay, easing, loop, playWhen}`.
- Кап частоты обновления анимаций: 60 Гц по умолчанию (настройка 30/60/120/240). Выше 60 Гц анимация визуально почти не отличается, но стоит CPU — предупреждаем в UI.
- Если все треки завершены/на паузе → рендер-поток засыпает (инвариант I3).

### 8.4 Лимиты (защита от «бомб»)

| Параметр | Лимит | Действие при превышении |
| --- | --- | --- |
| Размер файла | 512 КБ | отклонить |
| Глубина JSON | 16 | отклонить |
| Слоёв (всего, включая вложенные) | 64 | отклонить |
| Глубина вложенности `group` | 4 | отклонить |
| Точек в `poly`/`path` | 256 / 2048 символов | отклонить |
| Изображение (data-URI) | 256 КБ декодированное ≤ 512×512 | отклонить (защита от zip/image bomb: проверяем размеры ДО декодирования по заголовку) |
| Внешние URL | 0 | отклонить (разрешены только `data:image/png|webp;base64`) |
| Выражений | 32 bindings + 16 vars | отклонить |
| Анимаций | 16 треков | отклонить |
| Бюджет кадра на анимацию/реактив | 2 мс | деградация: снизить частоту, лог, предупреждение |

Реализовано в валидаторе-эталоне: [`tools/validate_presets.py`](../tools/validate_presets.py) (Python-версия для CI и для пользователя; в Rust — тот же набор правил, чтобы приложение и CI не расходились; сверка результатов — часть тестов).

## 9. Импорт из ИИ: детали конвейера

### 9.1 Нормализация входа

1. Обрезаем всё до первого `{` и после последнего `}` (аккуратно, с учётом вложенности и строк) — модели любят добавлять пояснения и \`\`\`json-заборчики.
2. Чиним типичное: одинарные кавычки → двойные, trailing commas, `red`/`rgba(0,255,136,1)` → `#00FF88`/`#00FF88FF`, `"1"` → `1`, комментарии `//` (удаляем), BOM.
3. Каждое авто-исправление логируем и показываем пользователю: «Исправлено автоматически: 3 цвета из rgba() в hex».
4. Если JSON несколько (модель выдала 3 варианта) — показываем список и даём выбрать, а не берём первый молча.

### 9.2 Валидация и сообщения об ошибках

- Формат ошибки: `layers[3].fill: ожидался цвет вида #RRGGBB или #RRGGBBAA, получено "neon-green"`.
- К каждой ошибке прикладываем: (а) фрагмент исходника, (б) ссылку на раздел DSL-доки, (в) кнопку «Копировать запрос на исправление».
- Ошибки группируем: сначала критичные (формат не тот вообще), потом по полям; показываем до 20, остальные — «и ещё N».

### 9.3 Песочница (только для P2-режима `script`)

Если в будущем разрешаем JS-canvas: QuickJS (`rquickjs`), изолированный runtime на каждый импорт, без DOM/сети/файлов/таймеров, allowlist из ~40 функций Canvas2D-подобного API (реализуем собственный контекст, рисующий в `tiny-skia`), бюджет 2 мс на кадр и 50 мс на инициализацию, детерминированный RNG, прерывание по счётчику инструкций. Режим по умолчанию выключен, включается в «Настройки → Продвинутое» с предупреждением.

### 9.4 Превью

Превью импорта = тот же рендер-бэкенд, что и оверлей (`tiny-skia` в растр → картинка в UI), поэтому WYSIWYG честный. Дополнительно «Применить на 15 секунд» прокидывает пресет в живой оверлей и откатывается назад по таймеру.

## 10. Хранилище и конфигурация

```
%APPDATA%\Overley\
├─ config.json            # настройки приложения (версия схемы, миграции)
├─ presets\
│  ├─ builtin\*.ovcross.json    # только чтение, обновляется с приложением
│  └─ user\*.ovcross.json       # пользовательские (в т.ч. source: ai)
├─ profiles.json          # профили приложений + правила матчинга
├─ history\               # последние 5 состояний каждого user-пресета
├─ assets\                # импортированные PNG/SVG (data-URI дублируем файлом, чтобы не раздувать JSON)
├─ logs\overley-YYYYMMDD.log  # ротация 7 дней / 10 МБ
├─ cursor-backup\*.cur    # бэкап системных курсоров (если включён system-blank)
├─ cursor.lock            # watchdog-файл
└─ cache\                 # растровые кэши статичных прицелов (пересоздаётся)
```

- **Источник истины — JSON-файлы** (читаемые, версионируемые, переносимые). SQLite — только индекс/кэш (поиск по галерее, история), пересоздаётся из JSON. Это упрощает бэкап, шаринг и отладку: пользователь может открыть файл блокнотом.
- **Атомарная запись:** пишем во временный файл → `FlushFileBuffers` → `MoveFileEx(REPLACE_EXISTING)`. Никаких полузаписанных конфигов при краше.
- **Single writer:** все изменения состояния проходят через один сервис `Store` в ядре; UI отправляет команды, получает события. Это исключает гонки «UI и watcher пишут одновременно».
- **Миграции:** у каждого файла `schemaVersion`; при загрузке — цепочка миграций v1→v2→…; неизвестная более новая версия → не ломаем, читаем в режиме совместимости и предлагаем обновить приложение.
- **Portable-режим:** если рядом с exe есть файл `portable.txt` или папка `data/` — все пути перенаправляются туда.

## 11. Взаимодействие ядра и UI (`ControlChannel`)

Единый контракт, реализуемый in-process (Tauri) или через named pipe (если UI вынесен в процесс):

**Команды (UI → ядро):** `applyPreset(id)`, `previewPreset(dsl)`, `tryOnFor(ms)`, `savePreset(dsl)`, `importPayload(text) → {ok, preset, warnings[], errors[]}`, `buildAiPrompt(locale, description) → text`, `setProfile(...)`, `toggleOverlay(visible)`, `restoreCursor()`, `getDiagnostics()`.

**События (ядро → UI):** `presetApplied`, `profileChanged`, `overlayVisibilityChanged`, `cursorModeChanged`, `fullscreenExclusiveDetected`, `importFinished`, `perfSample`, `error`.

**Правило:** UI никогда не держит состояние, которое является истиной. Истина — в ядре. UI закрывается/падает — оверлей продолжает работать по последнему применённому пресету.

## 12. Модель угроз (импорт внешнего контента)

| Угроза | Вектор | Митигция |
| --- | --- | --- |
| Произвольный код | Пользователь вставляет JS/HTML вместо JSON | DSL декларативен; `script`-режим выключен и изолирован (QuickJS); в UI-превью — CSP `default-src 'none'`, никакого `<iframe srcdoc>` с сырым контентом |
| SSRF/трекинг | `"src": "https://attacker/x.png"` | Запрет любых URL, только data-URI; негативный тест в CI; приложение в игровом режиме не имеет сетевых вызовов вообще |
| Image bomb | PNG 1×1 → 20000×20000 | Читаем заголовок до декодирования, лимит 512×512 и 256 КБ |
| Resource exhaustion | 10 000 слоёв, 256 анимаций | Лимиты §8.4 + бюджет кадра 2 мс + деградация |
| Path traversal | имя пресета `..\..\evil` | Санитизация имён файлов, id только `[A-Za-z0-9_-]`, хранение по внутреннему UUID |
| Prototype pollution / десериализация | `__proto__` в JSON | Запрещённые токены в валидаторе; serde со строгой типизацией, `additionalProperties` отклоняются |
| Prompt injection в метаданных | `meta.name` с инструкциями для ИИ при повторной генерации | При сборке follow-up промпта метаданные экранируются и обрезаются; имя ≤ 64 символа |
| Повреждение конфига | краш во время записи | Атомарная запись + бэкап предыдущей версии + восстановление |
| Невосстановленный курсор | `taskkill /F` во время `system-blank` | Watchdog-файл + восстановление при старте + CLI `--restore-cursor` |

## 13. Производительность: бюджет и техники

| Статья | Бюджет | Техника |
| --- | --- | --- |
| ОЗУ ядра | ≤ 15 МБ | без тяжёлых зависимостей, UI-окно уничтожается, кэши растров ограничены (LRU 8 МБ) |
| CPU в простое (статичный прицел) | 0 перерисовок | dirty-событийная модель, render thread спит |
| CPU с анимацией @60 Гц | ≤ 1,5% ядра | кэш статичной части, обновление только изменившихся props, без аллокаций в кадре (`SmallVec`, предаллоцированные буферы) |
| Present | ≤ 0,5 мс | flip-model, 2 буфера, waitable object |
| Реактивность | ≤ 0,2 мс/кадр | RPN-VM, клампы, сглаживание на input-потоке |
| Горячий старт | ≤ 1,2 с | ленивая инициализация (сначала окно+прицел, потом индексы/кэши) |
| Применение пресета | ≤ 50 мс | компиляция DSL быстрая, кэш брашей по хешу |
| I/O | только при изменениях | никакого периодического сохранения, журнал — append с буферизацией и сбросом раз в 5 с |

**Замеры — часть CI:** снапшот ОЗУ/CPU на каждом релизе (скрипт поднимает приложение в headless-режиме с эталонным пресетом на 60 с и пишет метрики в артефакт). Регрессия > 15% блокирует релиз.

## 14. Отказоустойчивость

- **Headless-режим ядра:** `overley.exe --render-test preset.json --out out.png` — рендер без окна (для CI/golden-тестов) и `--restore-cursor`, `--diagnostics`.
- **Паника-деградация:** если DComp/D2D не создались → CPU-fallback; если и он не работает → OSD «оверлей недоступен» и приложение продолжает жить (UI и пресеты работают).
- **Изоляция сбоев UI:** падение WebView2 не трогает оверлей (окно настроек отдельное; в вынесенном варианте — отдельный процесс).
- **Логи:** структурированные (`tracing`), уровни, ротация; в лог не пишутся содержимое пресетов целиком и никакие персональные данные.
- **Краш-репорты:** opt-in, только стектрейс + версия + ОС + код ошибки; отправка через собственный endpoint или Sentry с явного согласия.

## 16. Расширяемость (фаза 2)

- **Пак-пресеты:** папка/ZIP с манифестом `pack.json` (имя, автор, лицензия, список файлов) — устанавливается в `presets\user\packs\`.
- **Темы оформления UI:** CSS-переменные + JSON-тема.
- **Виджет Xbox Game Bar:** отдельный target сборки, переиспользует DSL-компилятор, рисует в WebView-виджете Game Bar (pinning + click-through поддерживаются платформой).
- **Клиент облачной галереи:** REST + кэш; импорт по ссылке; рейтинг/лайки.
- **Linux/macOS:** DSL-компилятор и валидатор переносимы; заменяются бэкенды рендера (Wayland layer-shell / macOS `NSWindow` level `.screen-saver`) и источники ввода.
